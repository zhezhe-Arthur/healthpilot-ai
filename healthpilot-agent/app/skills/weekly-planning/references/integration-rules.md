# 七天计划整合规则

版本：草稿v0.1

本文为项目排程规则，不是医学指南。

## 一、整合对象

只整合当前需要且依据充分的内容：
- 运动与恢复。
- 饮食行动。
- 睡眠习惯。
- 用户愿意接受的心理支持。
- 慢性病管理和记录事项。

没有相关需求的领域可以不新增任务。
不以领域覆盖数量评价计划质量。

## 二、安排顺序

先了解：
- 用户本周目标。
- 固定工作、通勤、照护和其他安排。
- 已明确的复查或随访时间。
- 休息与已有健康限制。

然后：
1. 放入本周相关的固定事项。
2. 保留休息和现实生活空间。
3. 安排主要行动。
4. 加入确有价值的可选事项。
5. 检查重复、冲突与总体负担。

这是排程顺序，不是医学治疗优先级。

## 三、时间口径

- 使用业务提供的起始日期与用户时区。
- 起始日期不明时先确认。
- 正式 DRAFT 必须使用 Java 提供且已校验为周一的 weekStartDate，覆盖周一至周日。
- 任务星期使用 ISO 编号：1=周一，7=周日；日期 = weekStartDate + (星期编号 - 1) 天，不能当作滚动计划第几天。
- 非周一请求仅可形成不可提交的讨论草案；不得自动平移到周一。缺少合法业务日期时等待 Java/用户确认，不生成可保存的正式计划。
- 跨午夜的睡眠等事项明确所属日期口径。
- 只有日期明确时才安排具体日期。
- 模糊时间保留为范围或待确认，不制造精确性。

没有明确钟点需求时，可以使用“午餐时”“下班后”等表达，
但不能据此宣称已经消除全部时间冲突。

## 四、去重规则

识别行动目的与执行内容，而不只比较文字。

可以合并：
- 运动Skill和心理支持均提出的同一次轻松散步。
- 营养和睡眠均涉及的同一项晚间饮品调整。
- 慢病记录与每周反馈中重复的同一项已有数据整理。

合并时：
- 保留最必要的限制。
- 不重复累计时长、次数或完成量。
- 不把合并行动声称为已经验证的多重治疗。
- 用户不愿把某活动赋予心理健康含义时，
  可使用普通行动名称。

不能合并：
- 日期或实际目的不同的医疗待办。
- 不同人的记录。
- 条件、单位或完成状态不同的事项。

## 五、主要安排、替代与可选事项

明确区分：
- 主要安排。
- 时间受限时的替代方案。
- 用户可以不做的可选事项。

替代方案不与主方案同时计入任务量。
可选事项不应计入必须完成的目标。
休息日不是“没有完成任务的一天”。

## 六、冲突处理

### 时间冲突

优先调整可灵活安排的生活行动。
不要静默移动已明确的复查预约。

### 健康限制冲突

返回相关领域或列出待确认问题。
不自行生成新医学规则解决冲突。

### 偏好与一般建议冲突

寻找可接受的替代方式。
没有硬性安全限制时，不把单一生活方式强加给用户。

### 目标过多

与用户主要目标对齐，
减少非必要的新行动，允许其余领域维持原状。

## 七、慢性病管理和记录

纳入：
- 已明确且本周相关的复查、随访。
- 用户需要的已有记录整理。
- 当前必须遵守的生活限制。
- 需要确认的安排。

展示：
- 事项。
- 日期或时间范围。
- 当前状态。
- 下一步。

不必每天重复病名。
没有本周待办时，后台保留限制即可。

状态未知：
写“确认是否已完成”，
不直接列成未完成任务。

时间或检查不明：
写“确认复查安排”，
不自行指定检查项目和日期。

医生要求较频繁监测：
保留要求，可在周计划中集中说明，
不因此新增产品每日手动打卡。

## 八、心理支持与提醒体验

- 不默认每天加入心理活动。
- 不重复询问情绪或展示心理问题标签。
- 用户拒绝某类练习时不重新包装后强行加入。
- 没有新信息时，不反复展示相同警告。
- 非紧急提醒尊重用户偏好。
- 当前出现新的安全信息时仍需及时处理。

## 九、输出结构示意

在没有正式Schema时，可按以下顺序展示：

1. 本周重点。
2. 七天安排。
3. 简化选择。
4. 本周相关待办。
5. 待确认事项。
6. 与上周相比的主要变化。
7. 每周反馈内容。
8. 待用户确认说明。

每日安排不要求固定五个栏目。
可以自然描述少量行动，避免空栏目和重复背景说明。

## 十、验收问题

- 用户能否看懂本周最重要的事情？
- 每天是否有实际可用时间完成？
- 是否允许重复、休息、替代和不做可选项？
- 是否存在多个领域对同一事项给出不同要求？
- 是否把医疗待办误写成已预约？
- 是否将隐私信息不必要地展示在每日计划中？
